# Synthetic backup/restore rehearsal

Run through the PostgreSQL 17 service in `.github/workflows/ci.yml`. `restore-rehearsal.sh` accepts only the GitHub Actions service container ID and checks the official `postgres:17` image. It uses an internal socket and fixed synthetic database names; it accepts no external URL or production credential.

The drill starts from the clean two-actor baseline, commits a synthetic employee/detail/policy/holiday graph and recorded/cancelled leave through RPCs, makes a custom-format `pg_dump`, and restores into a newly created `hr_regression_restore_test` database. Creating an existing restore target fails; no target is dropped or overwritten. The source remains intact while source/restored checksums and security catalogs are compared. ACLs are preserved; global roles already exist in the same isolated cluster. Then graph, FK, balance, membership/RLS and RPC-only write assertions run, fixtures are removed by reserved identities, six rollback suites execute on the restored database, and source/restore return to the two-actor baseline.

The dump is ephemeral and removed when the script exits. It is not uploaded to artifacts. Auth is mocked; this does not test real Supabase Auth identities, sessions, providers, secrets, Storage objects, SMTP or separate-cluster role restoration. This is a synthetic mechanics test, not evidence of an actual production backup/restore or chosen recovery objectives. The real-data backup still needs a DB connection credential, approved encryption/key custody, and a separately verified restore destination. Never copy production data or credentials into this public repository or CI.

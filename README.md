# HR — ระบบข้อมูลพนักงานและวันลา

เว็บแอปภายในองค์กรสำหรับเจ้าของธุรกิจและฝ่าย HR เพื่อเก็บประวัติพนักงาน จัดการสิทธิ์วันลา และดูยอดคงเหลือที่ตรวจสอบย้อนหลังได้ เอกสารนี้เป็น **ข้อกำหนดและแผนพัฒนา** พร้อมผลดำเนินงานข้อ 1–5 และแผนงานสำหรับข้อ 6–7

**เปิดตัวอย่างเว็บ:** [HR บน Vercel](https://hr-lac-theta.vercel.app/) → กด “ดูตัวอย่างหน้าจอ” เพื่อดูโครงหน้าแดชบอร์ด หน้าเข้าสู่ระบบใช้ Supabase Auth แล้ว และ `/workspace` อ่านข้อมูลจากฐานข้อมูลหลังตรวจสิทธิ์ ส่วน `/preview` ยังคงเป็นตัวอย่างสาธารณะไม่มีข้อมูลจริง ข้อ 2 สำเร็จตามการรับงานของผู้ใช้แล้ว โดยเก็บการทดสอบเปิดบัญชีเพิ่มเติมไว้เป็นงานติดตาม

## จุดประสงค์และขอบเขต

- รวมข้อมูลพนักงานไว้ในที่เดียว ค้นหาและแก้ไขได้โดยผู้มีสิทธิ์
- ตั้งโควตาวันลาแยกประเภทตามมาตรฐานบริษัท และปรับเป็นรายคนเมื่อจำเป็น
- บันทึกวันลาเต็มวันหรือครึ่งวัน แล้วเห็นยอดคงเหลือทันที พร้อมประวัติย้อนหลัง
- เก็บข้อมูลจริงบน Supabase และนำเว็บขึ้น Vercel เมื่อพัฒนาและทดสอบเสร็จ

| เรื่อง | ข้อกำหนดรุ่นแรก |
| --- | --- |
| ผู้ใช้ | เจ้าของธุรกิจและ HR ล็อกอินได้ ทั้งสองกลุ่มดูและแก้ไขข้อมูลได้เท่ากัน; พนักงานยังไม่มีบัญชีใช้งานเอง |
| ประวัติพนักงาน | ชื่อ–นามสกุล รหัสพนักงาน ที่อยู่ ตำแหน่ง แผนก วันเริ่มงาน เบอร์โทร เอกสารประจำตัว ข้อมูลธนาคาร และผู้ติดต่อฉุกเฉิน |
| เอกสารประจำตัว | ระบุชนิดเอกสารและเลขเอกสารได้ รองรับบัตรประชาชนไทย บัตรชมพู และเอกสารอื่นของพนักงานต่างชาติ ไม่บังคับเลขทุกรายการให้มีรูปแบบเดียวกัน |
| วันลา | แยกประเภท เช่น ลาป่วย ลากิจ ลาพักร้อน; ประเภทและโควตามาตรฐานแก้ได้ และปรับโควตารายคนได้ |
| การบันทึก | เจ้าของหรือ HR บันทึกแทนพนักงาน บันทึกสำเร็จแล้วหักสิทธิ์ทันที ยังไม่มีขั้นอนุมัติ |
| หน่วยวันลา | เต็มวันหรือครึ่งวัน (0.5 วัน) |
| วันที่นับ | เฉพาะวันทำงาน ข้ามเสาร์–อาทิตย์และวันหยุดที่ HR บันทึกในระบบ; แสดงจำนวนวันที่หักก่อนยืนยัน |
| รอบสิทธิ์ | 1 มกราคม–31 ธันวาคม ยอดเหลือไม่ยกไปปีถัดไป แต่ประวัติเก่ายังดูได้ |
| นอกขอบเขต | ลงเวลาเข้า–ออก เงินเดือน พนักงานยื่นลาเอง และการอนุมัติ |

จำนวนวันลาต่อประเภทต้องตั้งตามนโยบายบริษัทจริง ไม่สร้างค่าเริ่มต้นที่อ้างเป็นนโยบาย วันที่จ่ายเงินเดือนวันที่ 5 ไม่ใช่ตัวกำหนดรอบสิทธิ์วันลา

## หน้าจอและความเชื่อมโยงกับฐานข้อมูล

ใช้แนวภาพเดสก์ท็อป **ขาว–แดง** ที่ตกลงกัน: พื้นขาว ตัวอักษรเข้ม สีแดงสำหรับเมนูที่เลือกและปุ่มหลัก ออกแบบให้ใช้บนมือถือได้ด้วย ตารางรวมไม่แสดงเลขเอกสารหรือบัญชีธนาคาร

| หน้าจอ | การใช้งาน | อ่าน/เขียนข้อมูล |
| --- | --- | --- |
| เข้าสู่ระบบ | เข้าระบบและออกจากระบบ | Supabase Auth, `app_users` |
| ภาพรวม | จำนวนพนักงาน คนลาวันนี้ ยอดคงเหลือ รายการลาล่าสุด วันหยุดถัดไป | `employees`, `leave_entries`, `leave_entry_days`, `leave_entitlements`, `holidays` |
| รายชื่อพนักงาน | ค้นหาชื่อ รหัส แผนก; ดูยอดลารายประเภท; เปิดรายละเอียด | `employees`, `leave_entitlements`, `leave_entry_days` |
| ประวัติพนักงาน | เพิ่ม/แก้ไขข้อมูลทั่วไป เอกสาร ธนาคาร ผู้ติดต่อฉุกเฉิน; ดูโควตาและประวัติลา | `employees`, `identity_documents`, `bank_accounts`, `emergency_contacts`, `leave_entitlements`, `leave_entries` |
| บันทึกวันลา | เลือกคน ประเภท ช่วงวันที่ เต็ม/ครึ่งวัน; ดูวันที่นับและยอดหลังหักก่อนยืนยัน | อ่าน `leave_types`, `leave_entitlements`, `holidays`; เขียน `leave_entries`, `leave_entry_days` |
| ประวัติวันลา | กรองตามพนักงาน/ประเภท/ปี ดูรายละเอียด แก้ไขหรือยกเลิก | `leave_entries`, `leave_entry_days`, `audit_events` |
| ตั้งค่า | ประเภทลา โควตามาตรฐานรายปี วันหยุดราชการ/บริษัท | `leave_types`, `leave_policy_defaults`, `holidays` |

ข้อมูลอ่อนไหวแสดงในหน้ารายละเอียดหลังล็อกอิน โดยซ่อนบางส่วนจนกว่าผู้ใช้จะเปิดดูช่องนั้น สถานะว่าง โหลดข้อมูล และข้อผิดพลาดต้องสื่อสารเป็นภาษาไทยชัดเจน

## สถาปัตยกรรมที่เสนอ

ใช้ **Next.js + TypeScript** สำหรับเว็บและการประมวลผลฝั่งเซิร์ฟเวอร์, **Supabase Auth + Postgres** สำหรับตัวตนและข้อมูล, **Vercel** สำหรับโฮสต์เว็บ ปัจจุบันโครงเว็บ ฐานข้อมูล RLS และโค้ดเชื่อม Auth ถูกสร้างแล้ว ส่วนธุรกรรมบันทึกวันลายังเป็นงานข้อ 5

```text
เจ้าของ / HR ในเบราว์เซอร์
  → Next.js บน Vercel: UI, ตรวจข้อมูลที่ส่งมา, ตรวจเซสชัน
  → Supabase Auth: ตัวตน
  → Supabase Postgres: ตาราง, Row Level Security (RLS), ธุรกรรมบันทึกวันลา
```

ยอดคงเหลือคำนวณจากโควตาและรายการลาจริง ไม่เก็บ `remaining_days` เป็นค่าที่แก้ได้อิสระ การบันทึก/แก้ไข/ยกเลิกต้องตรวจยอดซ้ำในธุรกรรมเดียวที่ฐานข้อมูล เพื่อป้องกันการกดพร้อมกันแล้วใช้สิทธิ์เกิน

### ตารางข้อมูลที่วางแผน

| ตาราง | หน้าที่ |
| --- | --- |
| `app_users` | ผูก `auth.users.id` กับบทบาท `owner`/`hr` และสถานะเปิดใช้งาน; เพิ่มบัญชีโดยผู้ดูแลเท่านั้น |
| `employees` | พนักงาน รหัสไม่ซ้ำ ข้อมูลทั่วไป สถานะทำงาน/พ้นสภาพ |
| `identity_documents` | ประเภท เลขเอกสาร ประเทศผู้ออก วันหมดอายุถ้ามี; พนักงานหนึ่งคนมีได้หลายเอกสาร |
| `bank_accounts` | ธนาคาร ชื่อบัญชี เลขบัญชี บัญชีหลัก |
| `emergency_contacts` | ชื่อ ความสัมพันธ์ เบอร์โทร ลำดับความสำคัญ; มีได้หลายคน |
| `leave_types` | ชื่อประเภทลา สถานะใช้งาน ลำดับแสดงผล |
| `leave_policy_defaults` | โควตามาตรฐานตามประเภทลาและปี |
| `leave_entitlements` | โควตาจริงของพนักงานแต่ละคน × ประเภท × ปี; ระบุที่มาและเหตุผลหากปรับรายคน |
| `holidays` | วันที่และชื่อวันหยุดที่ HR เพิ่ม/แก้ไข |
| `leave_entries` | พนักงาน ประเภท ช่วงวันที่ เหตุผล สถานะ `recorded`/`cancelled` ผู้บันทึก เวลา |
| `leave_entry_days` | วันที่ถูกหักจริง 0.5 หรือ 1.0 วันต่อรายการ เพื่อคงประวัติแม้แก้ปฏิทินวันหยุดภายหลัง |
| `audit_events` | ผู้กระทำ เวลา รายการที่เปลี่ยน และค่าก่อน/หลังเท่าที่จำเป็น |

ใช้เขตเวลา **Asia/Bangkok** เพื่อตัดสินว่า “วันนี้” คือวันใด และใช้ชนิดวันที่สำหรับวันลา/วันหยุด ช่องจำนวนวันรับทีละ 0.5 วันและห้ามติดลบ ข้อมูลเอกสาร ธนาคาร และผู้ติดต่อฉุกเฉินแยกตารางเพื่อควบคุมและตรวจสอบได้ชัดเจน

### กติกาการคำนวณวันลา

`คงเหลือ = โควตาของพนักงานในปีนั้น − ผลรวมวันของรายการสถานะ recorded ในปีเดียวกัน`

1. แยกช่วงลาเป็นรายวัน ข้ามเสาร์–อาทิตย์และวันที่อยู่ใน `holidays`
2. ครึ่งวันต้องเป็นวันทำงานวันเดียวและระบุครึ่งเช้าหรือครึ่งบ่าย; เต็มวันหัก 1 วัน ครึ่งวันหัก 0.5 วัน
3. ช่วงลาคร่อมปีต้องหักโควตาของแต่ละปีตามวันที่จริง ไม่เอาสิทธิ์ปีก่อนมาชดเชยปีใหม่
4. ไม่รับรายการที่ไม่มีวันทำงาน ยอดไม่พอ หรือซ้ำทับกับรายการที่บันทึกอยู่; เต็มวันชนกับรายการใดก็ไม่ได้ และครึ่งวันช่วงเดียวกันชนกัน
5. แสดงวันที่นับและยอดหลังหักให้ตรวจ ก่อนบันทึก; หากบันทึกไม่สำเร็จ ต้องไม่หักยอดบางส่วน
6. การยกเลิกเปลี่ยนสถานะเป็น `cancelled` และคืนยอดโดยไม่ลบประวัติ; การแก้ไขบันทึกผู้แก้และเหตุผล
7. วันที่ 1 มกราคมเริ่มโควตาใหม่ตามค่ามาตรฐานของปีนั้น โดยการปรับรายคนมีผลเฉพาะปีที่ระบุ และไม่ยกยอดเหลือของปีก่อน

**นโยบายที่ต้องกรอกก่อนใช้ข้อมูลจริง:** ประเภทลาและโควตาจริง วันหยุดบริษัทจริง และเงื่อนไขลาเกินสิทธิ์ รุ่นแรกวางแผนให้ *ไม่อนุญาตลาเกินสิทธิ์* เพื่อป้องกันยอดคลาดเคลื่อน

## การเข้าถึงและปกป้องข้อมูล

รีโปเป็นสาธารณะ ห้าม commit ข้อมูลพนักงานจริง ไฟล์ `.env.local` รหัสผ่าน หรือ Supabase secret/service-role key ใช้เฉพาะ **publishable key** ในเว็บ เปิด RLS บนทุกตารางที่เปิดผ่าน Supabase Data API; ให้อ่าน/แก้ได้เฉพาะบัญชี `app_users` ที่เปิดใช้งานและมีบทบาท `owner` หรือ `hr` การล็อกอินเพียงอย่างเดียวไม่ถือว่าได้รับสิทธิ์

ตรวจสิทธิ์ทั้งหน้าจอและฝั่งฐานข้อมูล รวมถึงการเข้าหน้าผ่าน URL โดยตรง ไม่เชื่อจำนวนวันลาที่เบราว์เซอร์ส่งมา ทดสอบว่าคนไม่ล็อกอินหรือบัญชีถูกปิดเห็นข้อมูลไม่ได้ ก่อนนำข้อมูลจริงเข้า ต้องกำหนดวิธีสำรอง/กู้คืนและระยะเก็บข้อมูลตามนโยบายองค์กร

## แผนเขียนโค้ดตามลำดับ

ทุกช่วงควรจบด้วยสิ่งที่ทดลองได้จริง; ข้อ 1–3 สำเร็จแล้ว ข้อ 3 ผ่านการตรวจรับครบ 9/9 งานย่อย (100%) และผู้ใช้ยืนยันให้ปิดงานเมื่อ 2026-09-30 ข้อ 4 ผ่านครบ 9/9 งานย่อย (100%) รวม integration/concurrency/browser QA และ cleanup fixtures; หลักฐานอยู่ใน checklist ด้านล่าง ข้อ 5 ผู้ใช้รับงานหลักแล้วเมื่อ 2026-10-01 โดยเลื่อน HR browser QA; cleanup ชุดทดสอบเสร็จแล้วเมื่อ 2026-10-01; ข้อ 6 ตรวจรับครบตามขอบเขต owner และมือถือจำลองแล้ว โดย HR browser QA ยังเลื่อน; ส่วนข้อ 7 ยังไม่ครบ การเปิดบัญชีเพิ่มเติมและ SMTP ของข้อ 2 ยังคงเป็นงานติดตาม

1. **โครงเว็บและดีไซน์:** สร้าง Next.js/TypeScript หน้าเข้าสู่ระบบ โครงหน้า ธีมขาว–แดง และรูปแบบมือถือ; ตรวจสถานะว่าง โหลด และผิดพลาด
2. **ฐานข้อมูลและสิทธิ์:** สร้าง migration ของตาราง ความสัมพันธ์ ข้อจำกัด index และ RLS; เชื่อม Supabase Auth; ทดสอบบัญชีที่มี/ไม่มีสิทธิ์
3. **ทะเบียนพนักงาน:** รายชื่อ ค้นหา เพิ่ม แก้ไข รายละเอียด เอกสาร ธนาคาร ผู้ติดต่อฉุกเฉิน; ทดสอบรหัสซ้ำและข้อมูลไม่ครบ
4. **นโยบายวันลา:** จัดการประเภท โควตามาตรฐานรายปี การปรับรายคน และวันหยุด; ทดสอบปีใหม่และสิทธิ์เฉพาะคน
5. **บันทึกวันลา:** แสดงตัวอย่างวันที่หัก บันทึกเต็ม/ครึ่งวัน ตรวจยอด กันวันทับซ้อน แยกปี ยกเลิก/แก้ไข และ audit; ทดสอบคำขอพร้อมกัน
6. **แดชบอร์ดและประวัติ:** ดึงยอดจริงจากฐานข้อมูล เพิ่มตัวกรองและรายการล่าสุด; ตรวจว่าตัวเลขทุกหน้าเท่ากัน
7. **ตรวจพร้อมใช้และ deploy:** ทดสอบเส้นทางหลัก สิทธิ์ ภาษาไทย มือถือ และการคำนวณ; ตั้งค่า production บน Supabase/Vercel; ทดสอบก่อนนำข้อมูลจริงเข้า

| **6.6 ยอดและประวัติรายพนักงาน** | เชื่อมหน้าพนักงานไปประวัติที่กรองคนและปีไว้; แสดงประเภท โควตา ใช้แล้ว คงเหลือ และสถานะสิทธิ์; ลิงก์กลับรายการและปุ่มบันทึกใช้ flow ข้อ 5 | คน/ปี/ประเภทเดียวกันได้ยอดเดียวกันทุกหน้า; cancelled คืนยอด; ไม่มี entitlement ไม่แสดงคงเหลือ 0 แบบมีสิทธิ์; พนักงานพ้นสภาพและประเภทปิดใช้งานยังตรวจประวัติได้ |
| **6.7 การอัปเดตหลังเปลี่ยนรายการ** | ตรวจ revalidation และ cache ของ create/edit/cancel และ quota/holiday changes; ทดสอบกลับจากรายละเอียดพร้อมตัวกรอง; แสดงโหลด/ผิดพลาดแยกจากข้อมูล 0 | หลัง mutation สำเร็จและ navigation/refresh ยอดและประวัติทุกหน้าตรงกัน; แก้ย้ายปี/ประเภทอัปเดตทั้งฝั่งเก่าและใหม่; mutation ล้มเหลวไม่แสดงยอดใหม่; วันหยุดแก้แล้วไม่เขียนทับวันที่หักของรายการเดิม; ยังไม่เพิ่ม Realtime |
| **6.8 UX ภาษาไทย มือถือ และสิทธิ์** | จัดตาราง/การ์ดและตัวกรองที่ 375px; labels และ keyboard navigation; empty/loading/error/retry; ไม่ใส่เลขเอกสาร ธนาคาร หรือเหตุผลส่วนตัวในรายการรวม | ไม่เกิด document overflow ที่ viewport 375px; เปิดรายละเอียดและล้างตัวกรองได้; คนไม่มีสิทธิ์/disabled/anon เข้าหน้าหรือเรียกชั้นอ่านข้อมูลไม่ได้; ใช้ owner browser QA ก่อน ส่วน HR browser QA คงเลื่อนตามผู้ใช้ |
| **6.9 ตรวจรับและส่งขึ้นเว็บจริง** | Unit tests นิยาม/ตัวกรอง; integration SQL เทียบ aggregate กับรายการจริง; browser QA desktop/375px; regression ข้อ 4–5; lint/typecheck/build; migration ถ้าจำเป็น deploy และ cleanup fixture เฉพาะรอบ | ผ่าน full/half เช้า–บ่าย วันหยุด ข้ามปี ยกเลิก แก้ย้ายปี ไม่มีสิทธิ์ ข้อมูลว่าง >1,000 แถว และตัวกรองร่วม; เก็บ commit/ผล deploy/หลักฐาน; ระบุข้อจำกัดมือถือจำลองและ HR ที่เลื่อน ไม่อ้างว่าผ่าน; fixture รอบนี้ cleanup แล้ว |

### 7. ตรวจพร้อมใช้และส่งมอบระบบ — แผนงานย่อย

**สถานะ: เริ่มดำเนินงานแล้ว — checklist ตรวจรับ 1/9 (7.2 ผ่านแล้ว)** — ข้อ 1–6 ผ่านตามขอบเขตที่บันทึกไว้ และ cleanup fixture ข้อ 5–6 เสร็จแล้ว. เว็บ deploy อยู่แล้ว; ข้อ 7 คือยืนยันความพร้อมใช้งานและการดูแลต่อ ไม่ใช่เพียง deploy ซ้ำ. บัญชี HR/เจ้าของเพิ่มเติมและ SMTP ยังมีงานติดตาม; ผล owner หรือ SQL role test ไม่แทน browser QA ของ HR.

**ผลดำเนินงานรอบแรก:** Sol ตรวจงาน/Luna พัฒนาแล้ว: CI, environment guard, auth tests, guarded local SQL runner และคู่มือดูแล/backup/release. Tests 85/85 + target-guard/controller 9/9, lint/typecheck/build ผ่าน; dependency audit ไม่พบช่องโหว่. ยังไม่ปิดข้อ 7 เพราะ fresh SQL ใน workspace ติดข้อจำกัด root แต่สร้างฐานใหม่และรัน regression 6 ชุด รวมสอง connection รอ advisory lock จริงและ cleanup ผ่านบน PostgreSQL แยกใน CI แล้ว; ผู้ใช้อนุมัติและตั้งค่า URL/public key/target ครบ 3 ตัวเฉพาะ Vercel Production แล้ว; redeploy source `d1863aa` เป็น Ready และตรวจหน้าเว็บจริงอ่านข้อมูล HRM ได้ตามเดิม; ถอด fallback และ target inference ใน source แล้ว (85 app tests +10 runner tests/lint/typecheck/build ผ่าน); synthetic pg_dump/pg_restore ลงฐานแยกผ่านบน PostgreSQL 17.11 พร้อมเทียบข้อมูล/สิทธิ์และรัน regression 6 ชุดหลังกู้; CI `36848091079` และ Production Ready ผ่าน, backup/restore ข้อมูลจริงยังไม่ได้ทำ (ชุดจำลองผ่านแล้ว) และยังต้องยืนยันนโยบายองค์กร/ผู้ดูแล. ผู้ใช้เลือก backup แบบไม่เพิ่มค่าใช้จ่ายบน Google Drive ส่วนตัว รายวัน เก็บ 30 วัน เป้าหมาย RPO 24 ชั่วโมง/RTO 4 ชั่วโมง; ผู้ดูแลจะระบุภายหลัง. [ผลตรวจและ gate ที่ค้าง](docs/phase7-acceptance.md) ระบุหลักฐานตามจริง; HR ยังเลื่อน.

**ฐานก่อนเริ่ม:** production มีพนักงานจริงเดิมหนึ่งคน บัญชีแอปสองบัญชี และไม่มีชุดทดสอบวันลาเหลือหลัง cleanup. ยังไม่ถือว่านโยบายลา โควตา และวันหยุดจริงได้รับการตั้งค่า. ไม่ใช้ production เป็นฐานทดสอบหลัก และไม่เผยแพร่ dump/ข้อมูลพนักงาน/อีเมลบัญชี/secret ใน public repo.

| **7.8 Release, monitoring และแผนถอยกลับ** | จัด runbook deploy/migration, ตรวจ build+commit+production, health/error monitoring ที่ไม่เก็บข้อมูลส่วนบุคคล, ผู้รับแจ้ง/ช่องทางและวิธีรับมือ; แยก rollback เว็บกับฐานข้อมูล | ทดลอง release/ถอยกลับในสภาพแวดล้อมทดสอบ; schema รองรับเว็บก่อนหน้า หรือมีแผนกู้ข้อมูล; deploy จริงมี smoke test; ไม่ถือว่า rollback Vercel จะ undo SQL; ไม่ส่งแจ้งเตือนหรือผูกบริการเสียเงินจากการวางแผนนี้ |
| **7.9 คู่มือ ส่งมอบ และสรุปตรวจรับ** | คู่มือ owner/HR การตั้งค่า การใช้งาน สำรอง/กู้คืน และเหตุขัดข้อง; รวมผล 7.1–7.8, commit/deploy, fixture cleanup, ผู้ดูแลและรายการงานติดตาม | หลักฐานทำซ้ำและผู้ดูแลทำตามคู่มือได้; ไม่มี blocker ค้างในขอบเขตที่รับ; ผู้ใช้รับทราบข้อจำกัดและอนุมัติเปิดใช้งานจริง; full owner+HR ต้องมี HR browser QA และระบบอีเมลที่ตรวจผ่าน |

**ลำดับดำเนินงาน:** เริ่ม 7.1 → 7.2 → 7.3; ทำ 7.4–7.6 ตามข้อมูล/สิทธิ์ที่มี → 7.7 → 7.8 → 7.9. ทำงานที่ไม่ขึ้นกับ HR ต่อได้ โดยคงรายการ HR เปิดไว้. ก่อนเปลี่ยน production ให้เตรียมผลตรวจและขั้นตอนที่ review ได้; ไม่ restore/delete ข้อมูลจริงหรือเพิ่มค่าใช้จ่ายโดยอาศัยแผนนี้อย่างเดียว.

**สิ่งที่ต้องตัดสินใจก่อนงานที่เกี่ยวข้อง:** ผู้ดูแลและผู้ใช้งานจริง; ประเภทลา/โควตา/วันหยุด; วิธีและงบ backup/SMTP/ฐานทดสอบ; ที่เก็บ backup และเป้าหมายการกู้คืน; ระยะเก็บข้อมูลตามนโยบายองค์กร. เสนอทางเลือกจากข้อมูลจริงเมื่อถึงงานนั้น ไม่เดาคำตอบหรือถือว่าผู้ใช้อนุมัติค่าใช้จ่ายแล้ว.

### เกณฑ์รับงานรุ่นแรก

- เจ้าของและ HR เข้าระบบได้; บุคคลอื่นเข้าถึงข้อมูลพนักงานไม่ได้
- เก็บประวัติพนักงานพร้อมเอกสารหลายประเภท บัญชีธนาคาร และผู้ติดต่อฉุกเฉินได้
- ตั้งโควตามาตรฐานและปรับรายคนได้; ยอดคงเหลือแยกประเภทตรงกับประวัติ
- ครึ่งวันหัก 0.5 วัน; ช่วงลาหลายวันข้ามเสาร์–อาทิตย์และวันหยุดที่ตั้งไว้
- ป้องกันลาเกินสิทธิ์และวันซ้ำทับ; บันทึกล้มเหลวแล้วไม่เกิดการหักบางส่วน
- ปีใหม่เริ่มโควตาใหม่ไม่ยกยอดเก่า แต่ดูประวัติปีก่อนได้
- ยกเลิกรายการแล้วคืนยอด และตรวจได้ว่าใครเปลี่ยนอะไรเมื่อไร
- เว็บบน Vercel อ่าน/เขียน Supabase production ได้จริงโดยไม่เปิดเผย secret

## Flow ตั้งแต่พัฒนาถึงใช้งานจริง

```text
ยืนยันประเภทลา/โควตา/วันหยุดจริง
  → สร้าง Supabase project สำหรับพัฒนาและ production
  → ทำ migration + RLS + บัญชี owner/HR
  → พัฒนาเว็บและทดสอบด้วยข้อมูลสมมติ
  → ทดสอบการคำนวณ สิทธิ์ และการแก้ไขข้อมูล
  → เชื่อม GitHub repo นี้กับ Vercel
  → ตั้งค่า environment variables บน Vercel
  → ใช้ migration กับ Supabase production และกำหนด Auth redirect URL
  → deploy → ทดสอบเว็บจริง → จึงนำข้อมูลพนักงานจริงเข้า
```

ตามคู่มือ Supabase สำหรับ Next.js ค่าที่เว็บต้องใช้คือ `NEXT_PUBLIC_SUPABASE_URL` และ `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` ซึ่งเป็น URL โปรเจกต์และ publishable key; key นี้ไม่ข้าม RLS ห้ามใส่ service-role/secret key ในตัวแปร `NEXT_PUBLIC_*` เมื่อมีโปรเจกต์ Supabase แล้ว ให้นำค่าจากหน้า Connect ใส่ `.env.local` สำหรับพัฒนาและ Environment Variables ของ Vercel สำหรับเว็บที่ deploy โดยไม่ commit ค่าในรีโป

เชื่อมรีโปกับ Vercel และเลือกโปรเจกต์ Next.js ตั้ง environment variables ของ production แล้วกำหนด Site URL/Redirect URLs ใน Supabase Auth ให้ตรงโดเมนที่ใช้จริง ทดสอบล็อกอิน/ออกและการสร้างข้อมูลด้วยบัญชีทดสอบบนโดเมน production ทุกครั้งที่เปลี่ยน schema ให้ตรวจ migration กับฐานทดสอบก่อนใช้กับ production และจัดการสำรองข้อมูลตามนโยบายที่เลือก

### ข้อจำกัดการส่งอีเมลที่ตรวจพบ (2026-09-30)

โปรเจกต์ยังไม่ได้เปิด custom SMTP บริการส่งอีเมลเริ่มต้นของ Supabase ส่งได้เฉพาะอีเมลสมาชิกทีมของโปรเจกต์ จึงยังไม่ยืนยันการเปิดบัญชีและกู้รหัสผ่านของเจ้าของทั้งสองครบวงจร ต้องเชื่อมบริการส่งอีเมลขององค์กรก่อนใช้งานกับผู้รับนอกทีม Supabase ดู https://supabase.com/docs/guides/auth/auth-smtp

### ผลทดสอบบัญชีเจ้าของจริง (2026-09-30)

ผู้ใช้ยืนยันว่าเปิดบัญชีและเข้าใช้งานด้วยอีเมลเจ้าของโปรเจกต์ได้แล้ว ตรวจฐานข้อมูลพบการยืนยันอีเมลและสมาชิก owner ที่เปิดใช้งาน ต่อมาผู้ใช้ยืนยันว่าออกจากระบบและลืมรหัสผ่านทำงานได้ดี และสั่งให้ปิดข้อ 2 เป็นสำเร็จ พร้อมเก็บสิ่งที่ยังไม่ทดสอบเป็นงานติดตาม บัญชีเจ้าของคนที่สองและการเปิดบัญชีเพิ่มเติมยังไม่ผ่านการทดสอบ ส่วน SMTP สำหรับผู้รับนอกทีม Supabase ยังต้องตั้งค่าเพิ่มเติม

**อัปเดต cleanup ข้อ 5 (2026-10-01):** ผู้ใช้สั่งล้างชุดทดสอบก่อน HR QA; guarded transaction ล้าง fixture พนักงาน 6 คน ประเภทลา 4 ประเภท รายการ 9 รายการ พร้อมวันหัก/request/audit/สิทธิ์/นโยบายและวันหยุดสมมติแล้ว. ตรวจซ้ำไม่เหลือ fixture และพนักงานจริง/บัญชีผู้ใช้เดิมไม่เปลี่ยน. ข้อความก่อนหน้าที่ระบุ cleanup ค้างเป็นประวัติก่อนการล้างรอบนี้; งานติดตามปัจจุบันเหลือ HR browser QA ซึ่งต้องเตรียม fixture ใหม่.
